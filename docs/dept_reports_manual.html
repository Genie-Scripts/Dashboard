1. これは何か

診療ダッシュボード本体（generate_html.py が作るWeb版）とは別立ての、 院内配布・印刷用のPDFレポートを生成する仕組みです。月1〜2回、部門会議や ミーティングでの配布を想定しています。

在院・新入院・全身麻酔手術・粗利・週末の入退院バランスを、部門ごと（診療科／病棟）に A4 1枚へまとめ、あわせて病院全体のサマリも自動生成します。

2. 生成される3つのPDF

ファイル内容ページ数の目安
診療科版_{基準日}.pdf 診療科ごとに1ページ（全診療科を連結・一括印刷用） 約20ページ
病棟版_{基準日}.pdf 病棟ごとに1ページ（全病棟を連結・一括印刷用） 約17ページ
病院全体サマリ_{基準日}.pdf 1ページ目=KPI＋グラフ／2ページ目=病棟別実績表／3ページ目=診療科別実績表 3ページ

出力先は dept_reports/{基準日}/ です。--split を付けると、 部門ごとの個別PDF（{基準日}/診療科/{診療科名}.pdf など）に分割されます。

PDFと一緒に 一手レビュー用のHTML（レビュー_{基準日}.html）も 出力されます。これは印刷物ではなく、配布前にAIコメントを確認・手直しするための 画面です（§5.5）。

3. 実行方法

3.0 関連する.shファイル（このリポジトリ全体の位置づけ）

リポジトリ直下には3つのシェルスクリプトがあり、それぞれ役割が異なります。 このマニュアルの対象は build_reports.sh だけです。他の2つは 診療ダッシュボード本体（Web版）の運用スクリプトで、部門別レポートPDFの生成には 関与しません。

ファイル役割実行タイミング
pull.sh 作業開始時に GitHub から最新コードを取得し、requirements.txtの 変更をライブラリへ同期する 作業を始める前に手動実行
deploy.sh 診療ダッシュボード本体（Web版）をビルド（generate_html.py・ 医業収支推計・自己完結HTMLを生成）し、コミット→GitHub Pagesへプッシュする。 git log に残る「Dashboard update: 日時 [M5-Pro]」の コミットはこのスクリプトによるもの（定期実行の自動化あり） 作業終了時、または定期実行
build_reports.shこのマニュアルの対象 部門別レポートPDF（診療科版／病棟版／病院全体サマリ）だけを生成する。 deploy.shとは独立しており、手動でダブルクリック実行する 運用（月1〜2回）。既定はレビュー運用＝生成後にレビュー画面が自動で開き、 一手を直して「PDF再作成」で確定してから配布する（§5.5） 部門会議・配布の前に手動実行
build_reports.shはdeploy.shの自動コミット/プッシュには 含まれません。PDF生成のみを行い、git へのコミットは行いません （dept_reports/はローカル出力専用）。

ダブルクリック実行（AppleScript/Automator）

build_reports.sh をダブルクリック、または Automator から呼び出します。 oMLX（一手のAI要約）が未起動なら自動で起動を試みます。

既定の流れ（レビュー運用・2026-07-05〜）：生成完了後に レビュー画面（レビュー_{基準日}.html）がブラウザで自動的に開きます。 一手を確認・修正 →「保存」→「PDF再作成」→ 画面内の「できあがりPDF」リンクから 印刷、が基本動作です（詳細は§5.5）。裏で動くレビューサーバは 無操作2時間で自動終了するため、後始末は不要です。 従来どおり生成だけして終わる場合は ./build_reports.sh --no-review。 --only／--limit（部分ビルド）を渡した場合は自動的に 従来動作になります。

初回生成を急ぐときは ./build_reports.sh --fast （一手の意味整合チェックを省いてLLM呼び出しを約半分にします）。「PDF再作成」は 生成キャッシュにより2回目以降は数秒で完了します（§5.5）。

コマンドライン（make）

# 既定（軸ごと連結＋AI一手）
make reports

# 一手を定型文のみ（oMLX不要・高速）
make reports AI=off

# 部門ごとの個別PDFに分割
make reports SPLIT=on

# 基準日を指定
make reports DATE=2026-05-31

直接実行（オプション詳細）

python scripts/build_dept_reports.py [オプション]
オプション説明
--data-dir DIRデータディレクトリ（既定: data）
--output-dir DIR出力先（既定: dept_reports）
--base-date YYYY-MM-DD基準日を指定（既定: データ最終日）
--axes dept,ward診療科版・病棟版のどちらか/両方（既定: 両方）
--no-ai「この期間の一手」をAI生成せず定型文のみにする
--only 診療科名特定の1部門だけ生成（確認・動作確認用）
--limit N先頭N件のみ生成（確認用）
--split部門ごとの個別PDFに分割
--keep-htmlPDF化前の中間HTMLも出力先に残す
--no-overridesoverrides.md（一手の手直し）を読み込まない
--no-cacheAI一手の生成キャッシュを使わず、毎回すべて再生成する
--quiet / -q進捗ログを抑制
Chromeが必要です：PDF化には headless Chrome（または Chromium / Edge）の --print-to-pdf を使用します。見つからない場合は HTML のみ出力されます。
初回生成を速くする：意味整合の第2パス検査（judge）を省くとLLM呼び出しが 約半分になります。build_reports.sh --fast、直接実行では環境変数 AI_NARRATIVE_JUDGE=0 を指定します。「PDF再作成」は生成キャッシュにより 2回目以降は数秒で完了するため、通常このフラグは不要です。

4. 各ページの見方

4.1 KPIカード

診療科・病棟は4枚、病院全体サマリは5枚（在院患者数・新入院・全身麻酔手術・粗利・ 週末在院維持率NEW）。 カード左の色帯・実績値の色が達成状況を表します。

色意味
緑（達成）目標達成（達成率100%以上）
橙（接近）目標に接近（90〜100%未満）
赤（未達）目標未達（90%未満）
グレー（—）目標未設定、または ※色評価の対象外（業務実態が一般部門と異なる科・病棟）

週末在院維持率＝土日平均在院 ÷ 平日平均在院。目標93%。病院全体サマリのKPIカードと、 病棟別／診療科別の実績表に表示されます。

4.2 グラフ A〜E（優先順位で配置）

部門の種別ごとに、優先度の高い順で配置が変わります（優先1位=全幅ヒーロー表示）。

種別優先順
外科系診療科全麻手術 → 粗利 → 曜日プロファイル → 新入院 → 在院
内科系診療科在院 → 粗利 → 新入院 → 曜日プロファイル
病棟病床利用率 → 新入院 → 曜日プロファイル
  • 実線＝当年実績、グレー線＝前年同期、破線＝目標（病棟は目標利用率）
  • 網掛け（緑/橙）は目標超/目標割の区間を表す。線の色そのものは成績ではない
  • 粗利チャートは確報の末尾に、点線＋中空マーカーで「当月見込み」を接続 NEW（実績が確定するのは翌月20日ごろのため、 直近月は診療実績ベースの推計値を暫定表示）

4.3 病院全体サマリ 2・3ページ目（実績表）

病棟別・診療科別の実績を一覧表で表示します。診療科別テーブルの右端は 「粗利予測達成率」＝当月見込み粗利 ÷ 目標です。

ICU・HCUも通常どおり色評価の対象ですNEW（以前は 業務実態の違いを理由に評価対象外＝グレー表示でしたが、目標・実績が揃っており 評価可能なため、2026-07-01 に対象へ含めました）。
※眼科は業務プロファイルが未整備のため、引き続き色評価の対象外です。

5. 「この期間の一手」の仕組み

各部門ページの右下（またはグラフの空きコマ）に、AIまたは定型文による 「今週/この期間の一手」を1件表示します。 2026-07-01 リニューアル

5.1 3トピックから自動選択

以前は「週末在院の平準化（病床管理）」一辺倒でしたが、現在は下記3トピックのうち 目標未達が最も大きいものを自動選択します。

トピック対象レバー（提案の方向性）
病床平準化診療科・病棟金曜集中の退院を平日へ分散／週末入院で空床補充
新入院診療科・病棟地域医療連携の強化／予定入院枠の調整
全麻手術外科系診療科のみ手術枠の稼働確認／執刀医との症例調整

目立った不足が無い部門は、従来どおり「病床平準化」を既定（在院が良好なら現状維持の 定型文）にします。

5.2 救命救急センター系病棟（4階A・4階C）は専用文言

4階A病棟・4階C病棟は緊急入院・院内転棟が中心で、他病棟のような 「予定入院の曜日調整」「地域医療連携（紹介元）への働きかけ」という業務前提が 成り立ちません。この2病棟だけ、トピックの選び方（平準化 or 新入院、どちらの 不足が大きいか）は共通ロジックのまま、文言だけ専用に差し替えています （転棟・転出判断の迅速化、週末含めた受け入れ体制・当直の維持、など）。

5.5 一手の手直し（レビューHTML／overrides.md）2026-07-05 新設

AI/定型文の一手を人がその場で書き直して配布できます。修正は dept_reports/overrides.md に保存され、再ビルドで該当部門だけ差し替わります。

使い方（推奨フロー）

  1. build_reports.sh（ダブルクリック）または make review を 実行すると、ビルド後にレビューHTML （dept_reports/{基準日}/レビュー_{基準日}.html）がブラウザで 自動的に開きます（ローカルサーバ経由。build_reports.sh は バックグラウンド常駐＝無操作2時間で自動終了、make review は Ctrl+C で終了）。make reports でもファイルは出力されます（手動で開く）。
  2. 直したい部門のコメント（本文／一手）をクリックして書き換えます。 印刷と同じ見た目のシート上で、チャート・KPIを見ながら直せます。 文字数メーター（本文90字／一手70字・超過は橙）がレイアウト崩れを防ぎます。
  3. 右上の「overrides.md へ保存」を押すと dept_reports/overrides.md に書き込み ます。make review（レビューサーバ経由）で開いていれば、 保存先は自動で正しい場所（ビルドが読むファイル）になり、ファイル選択は不要です。 ファイルとして直接開いた場合のみ、初回に保存先の選択が必要です （下書きはブラウザに自動保持）。
  4. 隣の「PDF再作成」を押すと、その場で再ビルドが走り差し替え済みのPDFになります （進捗表示つき・完了で画面も新しい版に自動更新）。2回目以降は生成キャッシュにより 数秒で完了します（同じデータの再ビルドではAIを呼び直さず、前回のコメントを そのまま再利用するため。データが変われば自動で作り直します）。
「PDF再作成」ボタンが使えるのは make review で開いたときだけです。 ブラウザのセキュリティ上、ファイルとして直接開いたHTMLからはローカルのコマンドを 実行できないため、その場合は案内が表示されます（make reports の再実行で 同じ結果になります）。再作成は同時に1本のみ・リクエスト内容によらず常に同じビルドを 実行するだけなので、外部から任意の操作をされる余地はありません（サーバは 127.0.0.1＝このMac内からのみ接続可）。ポートは既定 8768 番で、他のアプリが 使用中なら自動で隣の空き番号にずれます。このMacで動いている他のシステム （業務ハブ関連のサーバ等）には干渉しません。

仕様のポイント

  • 有効期限：差し替えには expires（既定＝基準日+14日）が付き、期限を過ぎると 自動で無視されます（古い文が翌月以降に残留しない）。レビューHTMLで保存し直すと延長されます。
  • 片方だけの差し替え可：本文だけ・一手だけの修正もできます。直していない側は レビューで見たAI文がそのまま再現されます（生成は決定論のため）。
  • 数値行は編集不可：全麻/新入院/病床利用率のハイライト行はデータ由来のため 編集対象外です。
  • 手動バッジと解除：差し替え済みの部門は次回レビューHTMLで「手動」バッジが付き、 「AI文に戻す」で解除（次回保存でブロック削除→次ビルドからAI文）できます。
  • 手編集も可：overrides.md は素朴なテキストです。 [診療科:整形外科] expires:2026-07-16 の行に続けて body:／action: 行を書きます。壊れたブロックは そのブロックだけスキップして警告し、ビルドは止まりません。
  • 再作成が速い理由（生成キャッシュ）：AI一手は同じ事実からは必ず同じ文に なるため、生成結果が dept_reports/_state/ にキャッシュされ、同じデータの 再ビルドで再利用されます（LLMを呼び直さない）。これにより「PDF再作成」は数秒で 終わります。キャッシュを使わず毎回すべて作り直すには --no-cache。
  • 保存先はビルドと同じ場所に固定：make review 経由の保存は サーバが dept_reports/overrides.md（ビルドが読むファイル）へ直接 書き込みます。手編集する場合も、必ずこの場所のファイルを編集してください （別フォルダに置いても反映されません）。
  • 読み込みを一時的に止めたいときは --no-overrides。

6. AI（一手の自動生成）について

要約LLMには oMLX（OpenAI互換ローカルAPI・Llama-3.1-Swallow-8B）を使用します。 oMLXが未起動、またはAPI呼び出しに失敗した場合は、自動的に定型文へフォールバック します（レポート生成自体は止まりません）。

ハルシネーション対策

LLMに数値の計算や事実の創作をさせないよう、次の対策を二重に行っています。

  • プロンプト設計：LLMには定性語（例:「目標を明確に下回っている」）だけを事実として渡し、 具体的な数値・原因・傾向は一切与えない。数値の再引用・新しい理由づけを禁止する指示を明記。
  • 機械的ガード（プロンプト指示だけに頼らない）：生成された本文・アクションに
    • 半角・全角数字が含まれる
    • 与えていない傾向・原因を示す語（「傾向」「稼働率」「逼迫」等）が含まれる
    • 危険な提案（在院日数の延長＝「延伸」「早期退院」等）が含まれる
    • 異常に長い（暴走出力）
    のいずれかに該当する場合は棄却して定型文にフォールバックします。
このガードは完全ではありません（未知の言い回しでの創作までは検知できません）。 それでも数値の捏造や、与えていない傾向・原因の主張は高い確率で検知して棄却します。

7. トラブルシューティング

症状対処
PDFが生成されずHTMLだけ出るGoogle Chrome / Chromium / Edge のいずれかをインストールしてください。
「この期間の一手」が定型文ばかりになるoMLXが起動しているか確認（build_reports.shは自動起動を試みます）。ハルシネーション棄却が多いだけの場合もあり、異常ではありません。
生成が遅いAI一手はユニットごとに逐次LLM呼び出しを行うため、初回は数分かかります。ただし「PDF再作成」（同じデータの再ビルド）は生成キャッシュで数秒です。初回も急ぐなら build_reports.sh --fast（意味整合チェックを省いてLLM呼び出しを約半分に）、または --no-ai（定型文のみ）を使用してください。
特定の1部門だけ確認したい--only 診療科名 で該当部門のみ・高速に個別出力できます（病院全体サマリは省略されます・レビュー画面も出ません）。
「PDF再作成」を押すと案内ダイアログが出て実行されないレビューHTMLをファイルとして直接開いています。build_reports.sh（または make review）で開いた画面から操作するか、ターミナルで make reports を再実行してください。
手直しを保存したのにPDFに反映されない①保存後に「PDF再作成」を押したか確認（保存だけでは反映されません）。②このアップデート前から開いたままのレビュー画面は一度閉じ、build_reports.sh（make review）を実行し直して開き直してください（古い画面は保存先が正しくない場合があります）。③手編集した場合、保存先が dept_reports/overrides.md になっているか確認してください（別フォルダに保存すると読み込まれません）。
「保存」でファイル選択が出る／保存できないmake review（レビューサーバ経由）で開いていれば、保存はサーバが正しい場所へ書き込むためファイル選択は出ません。ファイルとして直接開いた場合のみ、初回に保存先の選択（Chrome以外はダウンロード保存）になります。その場合の保存先は必ず dept_reports/overrides.md にしてください。
レビュー画面のボタンが効かない（時間を置いて開いた）レビューサーバは無操作2時間で自動終了します。build_reports.sh を再実行してください（保存済みの手直しは overrides.md に残っており、再ビルドで反映されます）。
ポートが使用中と表示されるレビューサーバは既定で 8768 番（このMac内限定）を使い、他のアプリが使用中なら自動で隣の空き番号にずれます。--port を自分で指定した場合のみエラーになるため、空き番号を指定し直してください。院内の他システムや業務ハブ側のサーバに影響を与えることはありません。
手直しした文がいつの間にか元に戻った仕様です。差し替えの有効期限（基準日+14日）を過ぎると自動で無効になり、AI文に戻ります（古いコメントの残留防止）。継続したい場合はレビュー画面で再度保存してください。
